# Findings

Read-only audit evidence:

- The API exposes 275 controller routes in a single `WebController`; authorization is implemented as repeated inline checks rather than framework guards.
- `v1/schools`, `v1/schools/:id`, and `v1/schools` have no authentication. The controller itself says production mTLS/JWT is still to be added.
- Guardian login currently issues a durable session from a phone number alone. The separate OTP functions exist, but this endpoint does not invoke them.
- Session tokens are stateless HMAC payloads containing role, without an expiry or revocation state. Cookies use a 30-day lifetime and omit `secure`.
- Production config defaults security-critical secrets and callback validation to known/empty development values instead of refusing startup.
- The initial dependency finding is remediated: `pnpm audit --prod` now reports no known vulnerabilities. Both Next.js apps are at 15.5.24; API dependencies are at patched Nest 11.1.18 plus patched parser/upload overrides.
- The RLS script passed its five assertions, but only probes guardian, teacher, and bursar reads in the demo database. It does not exercise write policies, token/role changes, other nine roles, or cross-tenant routing.
- OTPs now use `crypto.randomInt`, keyed/salted storage, timing-safe verification, five-attempt lockout, and a short resend window. Guardian phone-only sessions are disabled, and phone formats normalize consistently.
- Production OTP dispatch is still not implemented: the current route only exposes the code in non-production. Production login therefore requires a real WhatsApp/SMS/email delivery workflow before it can be called release-ready.
- Sessions are tenant-bound, signed, `HttpOnly`, `Secure` in production, and expire in 12 hours. They are not server-side opaque/revocable; role/session invalidation remains a known limitation.
- Provisioner routes now require a timing-safe control-plane token. The public Caddy edge no longer proxies the direct API hostname.

Dashboard rationalisation research (external findings; treat as reference data):

- Role dashboards should be task-first: teacher (today's classes, attendance, marking, homework); guardian (child updates, fees, timetable, messages); leadership (attendance, finance, academic exceptions, approvals); specialist staff (their assigned workflow only).
- Research sources consistently group school operations into People/Admissions, Academics/Attendance/Assessment, Finance, Operations, Communications, and Configuration. Duplicating the same outcome across separate modules increases training cost and permission mistakes.
- Every role needs row- and field-level scope. In particular, transport, library, welfare, finance, and safeguarding must not inherit broad learner data access.
- Evidence gathered via Agent Reach/Exa on 2026-09-29. Second query was rate-limited after the first result set; use primary sources for later validation.
- No HTTP security headers, proxy trust configuration, API health checks, deployment resource limits, or backup encryption/off-site replication are defined in the inspected runtime configuration.

Public-site and product-handoff findings:

- `frontend/apps/site/src/lib/appLinks.ts` provides a single `NEXT_PUBLIC_APP_ORIGIN` boundary for all public-site-to-product links. The intended production split is root domain for the site and `app.<domain>` for the product.
- The `/start` page already presents three appropriate paths: school owner setup, staff join, and guardian login. This is the correct foundation to retain.
- The home-page `ParentCta` posts directly to the guardian OTP route and promises that a code was sent. Production OTP dispatch is still deliberately unimplemented, so this is currently a misleading production-facing flow and must be replaced or explicitly gated until delivery exists.
- Contact information uses placeholders (`+254700000000`, `schools@mandela.school`); these must not be presented as production support channels until real contact values are configured.
- The site has useful foundation pages (product, schools, parents, teachers, pricing, stories, about, contact, legal) plus metadata, robots, sitemap, and application JSON-LD. Its biggest gap is credible, verified proof and a clear demo/product-preview bridge rather than more generic pages.

Role-navigation audit findings (2026-09-29):

- The visible sidebar is generated by `getBootstrap()` from `DEFAULT_NAV` plus `perm_matrix` grants; `school_settings.nav_json` is effectively ignored because the computed defaults are always non-empty. The legacy branding seed still writes a conflicting second navigation model.
- Counter default is task-appropriate (`Today`, `Visitors`, `Inquiries`, `Directory`), but migration `052_perm_matrix_grants.sql` grants Counter `money`, `operations`, and `insights`. The bootstrap merger therefore adds broad dashboard groups visible in the supplied screenshot, contradicting a counter-only workflow.
- `AppShell.tabToHref()` has no route contract. Several legacy labels fall through to generated paths that do not exist: driver (`Route`, `Manifest`, `Done`); dorm parent (`Rollcall`, `Exeats`, `My dorm`); janitor (`Repairs`, `Supplies`, `My zones`); librarian (`Issue/Return`, `Catalogue`, `Overdue`); patron (`Points`); HOD (`Department`, `Marks`, `Coverage`).
- Current `DEFAULT_NAV` fixes some legacy labels but the map and defaults remain separately maintained, so any role-navigation data drift becomes a silent broken link rather than a test failure.
- Live Counter verification: its intended routes (`Today`, Visitors, Inquiries, Directory) all render successfully. The former Money/Operations/Insights sidebar entries disappear after the navigation-contract fix, while the Counter dashboard retains its approved visitor and inquiry deep links.
- The route contract exposed one real frontend defect: `Operations` worked only by falling through to a generated URL, not by a declared route owner. It now has an explicit registry entry. All current default role tabs are covered by explicit route assertions.
- Payment learner selection was rendering the entire tenant roster at once. It now has accessible name/admission search, class filter, a five-row default limit, and a `View all N learners` control. Browser and axe verification show the new controls and zero WCAG A/AA violations on the money page.
- Icon audit correction: prior assertions did not include every active role-default tab. New coverage exposed seven missing first-level glyphs (`Home`, `Transport`, `Hostel`, `Facilities`, `Library`, `Houses`, `Exams`) which were falling back to the dashboard glyph. Each now has a distinct semantic icon, and `AppShell` fails fast for any undeclared tab instead of silently reusing a generic icon.
- Full module audit: the application has 41 canonical child modules across Money, Spend, People, Academics, Operations, Care, Insights, Settings, Mark, and Homework, plus role-only and cross-cutting routes. Current route/icon contracts cover every live sidebar entry; live browser behavior has been verified for Counter and Money only. The largest remaining operational risk is inconsistent page-level role gates, where some pages rely on RLS rather than an explicit UI redirect. Full evidence and priority queue: `docs/MODULE-AUDIT-2026-09-29.md`.
- Page-gate audit: 61 `/app` route pages exist. The strongest gates use explicit role allow-lists; a large staff-only set relies on RLS and may show unhelpful empty/reduced pages for roles that do not own the workflow. Documentation still describes Counter Calendar/grant-added navigation although the enforced product policy has changed.
- Mobile sub-navigation still silently replaced missing child glyphs with the generic dashboard icon, so the earlier sidebar fix was incomplete. The child icon registry is now strict at every shell consumer: a missing child icon fails visibly during development and contract tests instead of creating a reused icon in the product.
- Live role checks: Admin and Bursar land on their intended dashboards with role-appropriate sidebar modules and KPI/chart sections. Teacher lands correctly, but its Today page contained a static "Your tools" grid linking to five leadership/operations pages outside the teacher navigation (`Insights`, timetable, events, conduct, report cards). It is now limited to the four teacher-owned tasks: attendance, homework, class, and messages. A focused contract prevents that dashboard drift from returning.
- Cross-role icon verification exposed two remaining collisions that per-list tests missed: `Repairs`/`Facilities` and `Catalogue`/`Library`. Facilities now uses a hammer and Library a bookmarked-book glyph; the test now checks one deduplicated union of every active role label.
- Scale-management audit: existing report builder, exams, audit trail, payment learner picker, and learner roster already have focused filters. The shared Cards/List system defaulted to cards for every section, which made operational records unnecessarily card-like. The new list-first default retains dashboard cards. Learner list data currently does not include boarding state, so a boarding filter was intentionally not added rather than creating a non-functional control.
- 2026-09-29: Production-browser smoke confirms `/app/money` loads in List mode by default, retains the compact five-person payment picker, and exposes receipt/learner, class, method, state, and date filters. `/app/people/learners` likewise loads as a labeled searchable list with status, class, and gender controls. Dashboard `/app` remains card-first by contract.
